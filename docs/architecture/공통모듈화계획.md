# 공통 모듈화 및 도메인 분리 계획

데이터변환 영역은 Antigravity 담당으로 두고, API 내부의 합성/일괄/설문/더미 작업을
오케스트레이션 가능한 구조로 정리한다.

## 1. 공통 작업 런타임

- 대상: 단일 합성, 일괄 합성, 설문 합성, 대용량 더미데이터 생성
- 현재 1차 반영: `synthetic_api.application.services.job_runtime`
- 역할:
  - 터미널 상태 상수 통일
  - in-process 작업 스레드/취소 플래그 단일 관리
  - DB 기반 진행률 업데이트 콜백 공통화
- 다음 단계:
  - 취소 플래그를 메모리 dict에서 DB 필드로 이동
  - 외부 오케스트라의 workflow id를 내부 job id와 매핑

## 2. 작업 영속 모델

- 현재: `jobs`, `synthesis_batches`만 DB 기반이고 설문 작업은 메모리 dict 기반
- 목표:
  - 모든 장시간 작업을 `jobs` 또는 공통 `workflow_jobs` 테이블로 추적
  - `kind`, `request_json`, `result_json`, `workflow_id`, `error`, `package_zip` 보관
  - 서버 재시작 시 진행 중 작업을 명시적으로 실패/재시도 가능 상태로 복구

## 3. 합성 파이프라인 단계 분리

- 현재: `SyntheticPipeline.execute()`가 검증, PII, 전처리, 학습, 샘플링, 평가, 문서 생성, 패키징을 모두 담당
- 목표 단계:
  - `validate_input`
  - `profile_and_plan`
  - `mask_pii`
  - `prepare_training_frame`
  - `train_model`
  - `sample_valid_rows`
  - `evaluate_quality_privacy`
  - `build_review_documents`
  - `write_outputs`
  - `zip_package`
- 효과:
  - 단계별 재시도/타임아웃 설정 가능
  - 진행률 메시지 표준화
  - 오케스트라 activity 단위로 직접 매핑 가능

## 4. 일괄 처리 오케스트레이션

- 현재: 단일 `ThreadPoolExecutor(max_workers=1)`가 파일별 합성을 순차 실행
- 목표:
  - parent workflow: batch 상태 집계 및 최종 ZIP 생성
  - child workflow: 파일별 단일 합성
  - 파일별 실패는 batch 전체 실패로 전파하지 않고 결과 manifest에 기록

## 5. 설문 합성 서비스 분리

- 현재: `routes/v1/survey.py` 안에 요청 모델, 상태 저장소, 백그라운드 실행, 파일 저장이 혼재
- 목표:
  - `SurveySynthesisService`로 실행 로직 이동
  - 상태 저장은 DB 기반 공통 작업 모델 사용
  - route는 입력 검증과 service 호출만 담당

## 6. 제외 범위

- 데이터변환 `routes/v1/converter.py`는 Antigravity 담당 영역으로 유지
- 짧은 조회 API, 다운로드 API, 용어사전 API는 오케스트레이션 대상에서 제외
