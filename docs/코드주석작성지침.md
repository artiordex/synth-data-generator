# 코드 주석 작성 지침

이 문서는 저장소에서 직접 작성하는 Python, TypeScript, TSX 코드와 테스트의
주석·문서화 형식을 통일하기 위한 단일 기준 문서임. 특정 기관, 제품, 배포
환경에 종속되지 않으며 프로젝트의 모든 소스 패키지에 적용함.

## 1. 적용 범위와 기본 원칙

- 직접 작성한 소스 파일과 테스트 파일에 적용함.
- `node_modules`, `.venv`, `.uv`, `dist`, 캐시, 빌드 산출물, 외부 생성 파일에는 적용하지 않음.
- 주석은 코드의 동작을 그대로 반복하지 않고 목적, 제약조건, 설계 이유를 설명함.
- 설명문은 `~함`, `~임`, `~음` 형태의 단답식 종결어미로 통일함.
- 이모지는 코드와 주석에 사용하지 않음.
- 개인 PC의 절대경로를 기록하지 않고 저장소 상대경로를 사용함.
- 단순한 코드에는 불필요한 주석을 추가하지 않고 복잡한 의사결정에만 설명을 남김.

## 2. 파일 헤더

직접 작성하거나 구조를 변경한 소스 파일의 최상단에 표준 헤더를 작성함.
작성자는 이름 또는 팀명으로 통일하고, 수정일은 실제 코드 동작이나 구조가
변경된 경우에만 갱신함.

## 3. 함수와 메서드

### 3.1 일반 함수

독립 함수, 유틸리티 함수, 테스트 함수에는 함수 선언의 목적을 한 줄로 작성함.
데코레이터가 있으면 주석을 데코레이터보다 앞에 배치함.

```python
# 이미지의 밝기 분포를 계산하여 어두운 배경인지 판별함
def is_dark_image(img_gray: np.ndarray, threshold: float = 127.0) -> bool:
    return float(np.mean(img_gray)) < threshold
```

```typescript
// 입력 파일의 확장자를 정규화된 소문자로 추출함
export function extractExtension(fileName: string): string {
  return fileName.slice(fileName.lastIndexOf('.')).toLowerCase();
}
```

### 3.2 공개 함수와 재사용 API

외부에서 호출되는 함수, API 서비스, 재사용 컴포넌트에는 입력·출력·예외·
설계 제약을 상세히 작성함.

Python은 표준 `Args`, `Returns`, `Raises` 형식의 docstring을 사용함.

```python
# 작업 식별자로 작업 정보를 조회함
def get_job(job_id: str) -> Job:
    """작업 정보를 조회함

    Args:
        job_id: 조회할 작업 식별자임
    Returns:
        조회된 작업 정보임
    Raises:
        FileNotFoundError: 작업이 존재하지 않는 경우 발생함
    """
```

TypeScript와 TSX는 JSDoc 태그를 사용함.

```typescript
/** 파일을 업로드하고 변환 작업을 시작함
 * @param file 업로드할 파일임
 * @param targetFormat 변환 대상 형식임

 * @throws Error 파일 형식이 지원되지 않는 경우 발생함
 */
export async function uploadFile(file: File, targetFormat: string): Promise<string> {
  return startUpload(file, targetFormat);
}
```

### 3.3 클래스와 클래스 메서드

- 클래스에는 객체의 책임을 설명하는 docstring 또는 JSDoc을 작성함.
- 단순한 메서드는 한 줄 주석으로 목적을 설명함.
- 공개되거나 복잡한 메서드는 Python docstring 또는 TypeScript JSDoc으로
  매개변수, 반환값, 예외, 부작용을 설명함.
- 모든 메서드에 형식적인 태그를 반복하지 않고 실제 호출자에게 필요한 정보만
  작성함.

## 4. 인라인 주석과 관리 태그

복잡한 조건, 보안 검증, 파일 형식 보존, 재시도·취소 처리처럼 코드만으로
의도를 알기 어려운 부분에만 인라인 주석을 추가함. 허용 태그는 다음과 같음.

| 태그 | 용도 | 예시 |
|---|---|---|
| `NOTE` | 비직관적인 설계 이유를 설명함 | `# NOTE: 원본 순서를 보존하기 위해 정렬하지 않음` |
| `WARN` | 부작용이나 사용상 주의를 설명함 | `# WARN: 대용량 입력은 청크 단위로 처리함` |
| `TODO` | 향후 개선 작업을 기록함 | `# TODO: 스트리밍 파서를 추가함` |
| `FIXME` | 알려진 결함의 임시 우회를 표시함 | `# FIXME: 특정 라이브러리 버전의 호환성을 우회함` |
| `SECURITY` | 보안·개인정보·입력 검증 이유를 설명함 | `# SECURITY: 외부 엔터티를 차단하여 XML 주입을 방지함` |

태그 뒤의 설명도 `~함`, `~임`, `~음` 형태로 작성함.

## 5. 금지 규칙

- 이모지나 인코딩이 불명확한 특수기호를 주석에 사용하지 않음.
- `~합니다`, `~입니다`, `~한다` 같은 서술형 종결어미를 사용하지 않음.
- 코드 한 줄을 그대로 번역하는 주석을 작성하지 않음.
- 개인 PC의 절대경로, 비밀키, 토큰, 개인정보를 주석이나 헤더에 기록하지 않음.
- 사용하지 않는 구버전 코드를 장문 주석으로 보관하지 않음.
- 단순한 변수 선언, 명확한 반복문, 자명한 반환문에는 설명 주석을 남발하지 않음.

## 6. 파일별 점검 목록

커밋 전 다음 항목을 확인함.

1. 파일 형식에 맞는 헤더와 저장소 상대경로를 작성했는지 확인함.
2. 모든 직접 작성 함수와 메서드에 목적 주석 또는 상세 문서화를 작성했는지 확인함.
3. 공개 API의 입력, 출력, 예외, 부작용을 설명했는지 확인함.
4. 주석 종결어미가 단답식 형식으로 통일되었는지 확인함.
5. 이모지, 절대경로, 비밀정보, 죽은 코드 주석이 없는지 확인함.
6. 생성 파일과 외부 코드에 불필요한 주석을 추가하지 않았는지 확인함.

이 문서를 코드 주석 규칙의 정본으로 사용하며, 별도의 중복 주석 지침을
추가하지 않음.
